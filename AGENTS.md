# AGENTS.md — правила для ИИ-агентов (Claude Code и любых других)

Этот файл читается первым, до любого кода. Он главнее интуиции агента о том, «как обычно делают».

## Правило №0
Каждая рабочая сессия должна оставлять запускаемый и проверяемый результат.

## Правило №1
Если сомневаешься — упрощай. Нарастим позже.

## Правило №2
Каждое крупное улучшение должно быть видно глазами. Не просто «+10%» — новый способ переноски, новый юнит, новая анимация, новое поведение.

## Правило №3
Каждая новая механика должна менять действия игрока. Если она добавляет только новую цифру — скорее всего, она не нужна.

## Правило №4
Не проектировать «на будущее». Сначала простая работающая версия, потом расширение.

## Правило №5
Сначала доказать, что механика интересна. Потом усложнять. Первая версия может быть очень примитивной.

## Правило №6
Документация опережает код там, где речь идёт о новых системах. Новая механика — сначала абзац в `docs/`, потом код.

## Правило №7
Никаких систем только потому что «это крутая идея». Каждая механика должна давать игроку новое действие или новый значимый выбор.

## Правило №8 — матрица приоритетов
Прежде чем брать фичу в работу, оценить по двум осям: **необходимость** (критично ли для основного цикла?) и **трудоёмкость**. Сначала — высокая необходимость при низкой трудоёмкости. Всё, что не критично для работающего MVP, уходит в следующую итерацию, а не делается «заодно».

## Правило №9 — вертикальный срез
Цель F1–F7 — не «много систем», а один связный кусок игры, в который можно играть 3–5 минут и понять ядро, вид и тон. Типичная ошибка — полировать визуал, не доказав основной цикл. Заглушки в срезе допустимы, но их не должно быть видно на самом видном месте.

## Правило №10 — «готово» ≠ «отполировано»
Тестирование и багфикс регулярно занимают столько же времени, сколько целый предыдущий этап. Тикет считается закрытым только после проверки человеком, а не после «код написан».

## Правило №11
Все ответы ИИ-агента пользователю — на русском языке. Код, имена переменных, коммиты — как обычно (английский), но текст, обращённый к пользователю, только на русском.

## Технические правила
- Data-Driven: параметры (стоимость, урон, скорость) — в `.tres`-ресурсах, не хардкод в скриптах.
- Сохранения: JSON-словарь в `user://save.json` или `ConfigFile`. Сериализуются только данные, не ноды.
- Визуал: простые фигуры, чистые цвета, минимализм. Не пиксель-арт, не 3D.
- Маленькие тикеты: делай только то, что просит тикет из `docs/06_Development/Tickets.md`. Не добавляй не связанные функции.
- После выполнения тикета — обнови `docs/06_Development/Repo_Current_State.md` (одна страница: сделано / в работе / дальше) и отметь статус тикета.
- Проверка визуала: игра сохраняет скриншот вьюпорта в `screenshots/` по нажатию клавиши. Агент читает PNG по пути, а не получает картинку через буфер обмена. Подробности — `docs/06_Development/Verification.md`.
- `--headless` годится для проверки «грузится ли сцена», но отключает рендеринг — для скриншотов запускать Godot с окном.

## Чего не делать
- Не делать игру сложнее без необходимости.
- Не создавать десятки ресурсов.
- Не строить архитектуру на годы вперёд.
- Не превращать каждый бонус в процент.
- Не добавлять декоративные выборы без последствий.
- Не делать Светлых однозначно хорошими, Тёмных — однозначно злыми.
- Не делать длинные кат-сцены.
- Не делать смену летописцев (идея отклонена, см. `docs/04_Content/Chronicle.md`).
- Не превращать idle в обязательный микроменеджмент для всех игроков.
- Не пытаться сразу реализовать всю игру — см. `docs/06_Development/Roadmap.md`, двигаться по фазам.
- Не подтверждать «работает», не проверив запуском. Компилируемость ≠ работоспособность.
- Не оценивать «интересно ли» самостоятельно — это проверяет только человек за игрой (Правило №5).

## Порядок работы
1. Прочитать `AGENTS.md` (этот файл).
2. Прочитать `docs/06_Development/Repo_Current_State.md` — что уже сделано.
3. Прочитать `docs/06_Development/Tickets.md` — взять следующий тикет со статусом «Ждёт».
4. Реализовать ТОЛЬКО этот тикет.
5. Обновить `Repo_Current_State.md` и статус тикета.
6. Закоммитить с понятным сообщением.
